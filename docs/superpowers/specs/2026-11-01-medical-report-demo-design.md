# 医学影像报告系统 Demo 设计说明

## 1. 目标与已确认需求

为管理员演示医院报告模板配置，为医生演示加载模板、自动填入业务字段、编辑报告正文的完整流程。

- 独立 Demo，配置真实保存到数据库，刷新及重启后可重新读取。
- 采用 Yiitap 开源框架提供 Notion 风格编辑体验。
- 各医院的字段清单来自事先确认的需求，例如 A 医院表头 6 个字段、B 医院 5 个。
- 管理员配置表头和表尾样式及字段绑定，支持预设布局和手动布局调整。
- 采用用户已选择的“分区配置、整页预览”：分别编辑表头、表尾，组合为完整报告预览。
- 加载报告页面后调用后台接口，通过绑定关系自动填入字段；医生专注正文。
- 正文是一整块 Yiitap 自由编辑区域。
- 后续可增加常用诊断描述模板，供医生插入正文；本期不实现该模板库。
- 模板文档按 Tiptap Schema 兼容的 JSON 格式保存，而非仅保存 HTML 或截图。

## 2. 方案比较与选择

### 已选择：分区配置、整页预览

表头与表尾分别使用 Yiitap 编辑。医生页面的表头、表尾以只读方式渲染，正文独立使用 Yiitap 编辑。组合后的页面呈现完整报告。

优点：配置边界和编辑权限明确，方便分别验证绑定、布局及正文编辑。代价：管理员需要切换区域，跨区域效果通过整页预览确认。

### 未选择：同一编辑器配置整页

在同一 Yiitap 文档中编辑表头、正文和表尾。整页编排更直接，但需额外处理区域移动、删除及只读权限，增加 Demo 复杂度。

## 3. 建议默认项，随本设计一并确认

以下为实现建议，不视为用户此前已明确指定：

- 界面使用中文，采用简洁侧栏、轻边框、清晰留白的 Notion 风格。
- 表头、表尾在医生页面只读，医生只编辑正文。
- 第一版每家医院维护一份当前模板，提供两家示例医院。
- 模板配置有显式“保存”按钮；医生正文也支持显式保存并重新打开。
- 使用 Vue 3、TypeScript、Yiitap，Node.js 后端及 SQLite 本地数据库。具体依赖版本在实施时核验兼容性并固定。
- 使用真实本地 HTTP 接口返回虚构病例，不连接医院真实系统。
- 管理员、医生通过 Demo 入口切换，不实现正式登录、权限认证及多租户隔离。
- 数据库、源代码及测试产物均保存在本项目目录内。
- 手动布局指文档流内的字段拖动、排序、跨单元格放置及列宽调整；不提供画布式任意坐标定位。若需要绝对坐标定位，应在实施前调整设计。
- 报告预览呈现纸张式排版；本期不包含严格分页、打印适配或 PDF 导出。

## 4. 界面与使用流程

### 4.1 医院模板配置

选择医院后显示该院已确认字段清单和当前模板。表头、表尾通过切换区域分别编辑，每个区域均使用 Yiitap。

管理员可以：

1. 选择预设的 1、2、3 列布局，插入或调整布局块。
2. 从该区域的字段清单插入字段节点。
3. 拖动字段调整位置和顺序，调整列宽、文字样式、对齐及间距。
4. 编辑医院名称、报告标题等静态文本。
5. 查看和修改字段的接口路径绑定。
6. 查看带模拟数据的整页预览，然后保存配置。

预设布局与手动编辑操作同一份文档，不维护两套配置。向非空区域应用预设时保留字段和绑定；若无法无损重排，提示用户选择重新排布或取消，不能静默丢弃内容。

本期字段定义由示例数据预置，不做通用字段字典管理系统。管理员可调整字段展示标签，稳定的字段标识不变。保存前检查已确认字段是否全部出现且每个字段恰好出现一次；编辑过程中允许暂时缺失，保存时明确指出问题。

### 4.2 字段绑定

提供可见的绑定配置列表，列出字段名称、稳定字段标识、后台数据路径与样例值。

示例：`患者姓名 → patientName → patient.name`。

字段节点保存稳定的 `fieldId`；医院模板配置保存 `fieldId → 数据路径` 的映射。重命名标签或拖动节点不改变绑定。路径仅支持受限的点号属性访问，不执行表达式或脚本。

Demo 后台提供接口字段清单与样例数据，管理员从清单选择绑定目标。未知路径不允许保存；合法路径在某个病例中值为空时，显示 `—`。数值 `0` 不作为空值处理。

### 4.3 医生报告页面

1. 选择示例医院和该院示例病例。
2. 加载已保存的模板，再请求该病例的后台数据。
3. 根据绑定关系渲染表头、表尾。
4. 在中间的单一 Yiitap 区域编辑正文，包括段落、标题、加粗和列表等基础能力。
5. 点击保存，将正文 JSON 保存到数据库；重新打开恢复。

绑定字段的实际值不回写医院模板。患者数据加载失败时显示错误和重试入口，不沿用上一病例数据，也不显示填充成功。

医院或病例切换时清空旧数据，忽略已过期的接口响应。存在未保存的配置或正文时，应用内切换提示保存、放弃或取消。

## 5. 文档与数据设计

### 5.1 Schema 与保存内容

Tiptap Schema 定义可用节点、属性和嵌套规则；数据库保存符合 Schema 的文档 JSON。表头、表尾、正文各自为合法的 Tiptap 文档，医院模板记录将表头、表尾组合在一起。

建议在 Yiitap 扩展机制中实现 `reportField` 节点，至少保存 `fieldId` 和展示标签。布局和文字样式通过已注册的节点、属性及 marks 表达；不把关键布局只存为编辑器外部的临时 CSS 状态。

编辑器导出 JSON 后，重新加载必须恢复字段身份、绑定、布局和样式。编辑与预览使用一致的扩展集合和渲染规则，避免不支持的节点被丢弃。保存端验证 JSON 结构与字段引用；记录 `schemaVersion` 以便后续迁移。

Yiitap 原生布局及拖动能力的具体覆盖范围需在实施阶段验证；缺失能力以兼容 Tiptap 的扩展补齐，不能将任意坐标拖拽宣传为已有功能。

### 5.2 数据实体

- `hospitals`：医院标识、名称。
- `hospital_fields`：医院、区域、稳定字段标识、名称、类型和默认绑定路径。
- `report_templates`：医院、表头 JSON、表尾 JSON、绑定 JSON、Schema 版本、模板修订号、更新时间。
- `demo_cases`：医院、病例标识、虚构接口数据。
- `reports`：医院、病例、采用的模板修订号与模板快照、业务数据快照、正文 JSON、更新时间。

Demo 中每个病例维护一份报告。首次打开且保存报告时固定所用模板和数据快照；重新打开已有报告恢复快照，避免管理员修改模板后历史报告布局变化。演示新模板时使用未保存的新病例。正式版本管理、历史修订列表及归档审批不在本期实现。

### 5.3 后台职责

提供医院与字段列表、模板读取与保存、病例列表、病例数据、报告读取与保存接口。后端校验医院、病例和模板的归属关系及字段引用。

SQLite 持久化真实配置与报告正文。初始示例数据只在缺失时建立，重启不得覆盖管理员已保存的配置。

## 6. 示例数据建议

这些字段仅用于 Demo，不代表用户已提供真实医院需求：

- A 医院表头 6 项：患者姓名、性别、年龄、患者编号、检查项目、检查日期。
- B 医院表头 5 项：患者姓名、年龄、检查编号、检查部位、检查日期。
- A 医院表尾 3 项：报告医生、审核医生、报告时间。
- B 医院表尾 2 项：报告医生、报告时间。
- 每家医院准备多份虚构病例，覆盖正常数据、空值及年龄为 0 的情况。
- 正文默认留空，可显示编辑提示；演示文本不构成诊断生成能力。

## 8. 验收与测试

1. A 医院显示 6 个表头字段，B 医院显示 5 个，配置互不影响。
2. 管理员能通过预设布局及手动调整设计表头、表尾，绑定不会因调整布局或标签而失效。
3. 保存后刷新、重启服务仍能恢复模板 JSON、字段绑定和样式。
4. 保存缺失字段、重复字段、未知绑定路径或无效 JSON 时明确报错，不能假装成功。
5. 医生页面调用接口并正确填充字段，表头、表尾只读；正文可编辑、保存、重新加载。
6. 空值显示 `—`，数值 0 正常显示；接口错误有重试入口，无跨病例残留数据。
7. 旧报告不会被后续医院模板修改静默改变。
8. 对绑定解析、JSON 保存恢复、模板校验进行针对性测试；对数据库持久化进行接口测试；在浏览器中验证拖动、列宽调整、整页预览和正文编辑流程。
